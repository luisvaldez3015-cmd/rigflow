# Milestone 1 — Feasibility, environment and architecture

_Status: living document. Last updated 2026-10-16._

This report answers the six questions required before implementation starts:
what exists, which Maya/Python APIs matter, the proposed architecture, the
smallest useful MVP, the main technical risks, and the first files and tests.

## 1. What is already implemented

Nothing functional. The repository contained only a placeholder `README.md`
and `assets/icon.svg` generated by the project template. There is no previous
code to preserve, so the package layout below is a clean start.

### Relevant APIs

- `maya.cmds` for scene inspection, keyframes, constraints, baking, undo chunks.
- `maya.api.OpenMaya` (API 2.0) for matrix math and fast world-space sampling.
- `maya.mel` only to drive HumanIK, which has no Python API of its own.
- `maya.OpenMayaUI.MQtUtil` + `shiboken` to parent Qt widgets to Maya and to
  embed a model panel (`cmds.modelPanel`) for the viewport previews.
- `MayaQWidgetDockableMixin` for a dockable main window.

## 3. Proposed architecture

Guiding rule: **Maya-dependent code is isolated; everything that can be unit
tested without Maya lives in pure-Python packages.**

```
rigflow/
  core/         config, compat (Maya/Qt detection), errors, logging, session state
  skeleton/     PURE. Joint graph model, naming-convention analysis, topology labeling
  mapping/      PURE. Auto-matching with confidence, overrides, validation, presets
  scene/        MAYA. Detect meshes/joints/animation, import files, read skeletons, undo
  retargeting/  MAYA. Retargeter interface + HumanIK backend + matrix-based fallback + baker
  animation/    Clip model (pure) + clip library bound to the scene (Maya)
  ui/           MAYA/Qt. Qt shim, theme, widgets, main window, matching view, review view
  utils/        PURE helpers (vector math, strings)
tests/unit         pure tests (mayapy -m unittest, seconds)
tests/integration  maya.standalone tests (slower)
scripts/           installer, launcher, module file, test runner
docs/              user + developer documentation (GitHub Pages candidate)
examples/          scripts that build reproducible demo scenes procedurally
```

### Key design decisions

1. **Canonical humanoid roles = HumanIK slot names** (`Hips`, `Spine`, `Spine1`,
   `Neck`, `Head`, `LeftShoulder`, `LeftArm`, `LeftForeArm`, `LeftHand`,
   `LeftUpLeg`, `LeftLeg`, `LeftFoot`, `LeftToeBase`, fingers, mirrored right side).
   Mixamo uses exactly these names, HumanIK needs them for characterisation, and
   they are a well-understood industry vocabulary. Both skeletons are labeled
   against this template independently; the source-to-destination mapping is then
   derived by shared role. This makes "one skeleton has 3 spine joints and the
   other 5" an explicit, solvable case instead of a special case.
2. **Two evidence sources fused per joint**: naming analysis (tokenised names,
   many conventions: Mixamo/HIK, Unreal/MetaHuman, AdvancedSkeleton, Biped,
   Unity, Daz) and topology analysis (hips = first node with three large
   branches, legs go down, spine goes up, chest branches into arms and neck,
   sides decided by rest-pose X). Agreement gives green; a single source gives
   yellow; a conflict gives yellow or red with an explanation. Manual overrides
   are stored separately and survive recomputation.
3. **Retargeting backend behind an interface** (`prepare`, `preview`, `bake`,
   `cleanup`). Primary backend: HumanIK (proportion-aware, battle-tested, ships
   with Maya). Fallback backend: matrix-based rotation transfer with root
   translation scaling for cases HumanIK cannot characterise. A feasibility
   spike for driving HumanIK fully from Python is in progress (see section 5).
4. **Non-destructive by default**: imports go into a dedicated namespace, the
   preview is live (no keys written), the bake writes keys onto the destination
   joints or onto a new animation layer, every scene change runs inside an
   undo chunk, and facial/eye/jaw joints are explicitly classified as *ignored*
   by the labeler so they are never touched.
5. **UI framework**: PySide2 for 2023/2024 (verified) with a thin `rigflow.ui.qt`
   shim so PySide6 (2025+) works by changing imports in one place. UI never
   imports `maya.cmds` directly; it talks to `core.session` and service modules.
6. **Installation via Maya module file** (`rigflow.mod`), the same mechanism
   mGear and other professional tools use. A drag-and-drop `install.py` writes
   the module file and creates the shelf button. Uninstall = delete two files.

## 4. Smallest useful end-to-end MVP

> Import a Mixamo FBX (skeleton + animation), select an existing destination
> skeleton in the scene, auto-map joints (green/yellow/red), fix one mapping
> by hand, preview the retarget live, bake onto the destination joints on an
> animation layer, undo works, facial controls untouched.

Everything else (review window polish, presets, multiple clips, documentation
site, trailer) builds on this path. The MVP is "done" only when an integration
test reproduces it headlessly with procedurally generated skeletons.

## 5. Main technical risks and mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| HumanIK cannot be driven reliably without its UI (MEL procs assume UI state) | Primary backend unusable in batch/tests | **Resolved by the spike (2026-10-16):** characterise → retarget → bake works headless in Maya 2023 and 2024; the UI validity query is unreliable so RigFlow validates numerically. See `docs/developer/humanik-backend.md`. The matrix-based fallback is implemented regardless. |
| Joint orientation / local axes differ between rigs | Garbage rotations if copied naively | Never copy local rotations. HIK handles this natively; the fallback works in world space with rest-pose deltas re-expressed in the destination's rest frame. |
| Destination already animated, or facial rig shares the hierarchy | Data loss, broken rigs | Bake to an animation layer by default; only joints present in the mapping receive keys; facial/eye/jaw/twist joints are classified *ignored*; undo chunk around every operation. |
| Rigs where joints are driven by controls (FK/IK rigs) | Baking onto joints fights the rig | v1 bakes onto the skeleton that the user selects as destination. Documented limitation; control-rig baking is a later milestone. |
| Different units, frame rates and scene scale | Wrong speed/size | Read `currentUnit` for time and length; scale root translation by hip-height ratio; never hardcode 24 fps or cm. |
| Qt differences (PySide2 vs PySide6) | Tool fails to open on 2025+ | Shim module; avoid deprecated enums; a smoke test constructs every widget off-screen. |
| Portfolio pressure to show "perfect" results | Over-claiming | Documentation and trailer only show what integration tests reproduce. |

## 6. Initial files and tests

Created in this milestone:

- Repository hygiene: `.gitignore`, `LICENSE` (MIT), `CHANGELOG.md`, `CONTRIBUTING.md`, `README.md`.
- `rigflow/core/`: `config.py`, `compat.py`, `errors.py`, `logging.py`.
- `rigflow/skeleton/`: `model.py`, `roles.py`, `naming.py`, `topology.py`.
- `rigflow/mapping/`: `model.py`, `matcher.py`, `validation.py`, `presets.py`.
- `rigflow/utils/`: `math3d.py`, `strings.py`.
- `tests/unit/`: fixtures that build Mixamo-like, Unreal-like, AdvancedSkeleton-like and
  nameless skeletons in memory; tests for naming, topology, matching, overrides,
  validation and preset round-trips.
- `scripts/run_tests.py`: runs unit tests, optionally integration tests, through `mayapy`.

Next milestone (M2/M3) adds `rigflow/scene`, `rigflow/ui` and the first
integration tests; the retargeting backend follows the spike's conclusions.

## Licence recommendation

**MIT.** It is short, familiar to artists and studios, allows commercial and
in-house use without copyleft obligations (which would otherwise deter studio
adoption), and requires only attribution. Apache-2.0 adds an explicit patent
grant at the cost of a longer text; GPL would make studio adoption unlikely.
RigFlow only *calls* Autodesk Maya and HumanIK through their public APIs; no
Autodesk code is redistributed. Mixamo or other third-party animations must
never be committed to the repository; all demo content is generated by scripts.
